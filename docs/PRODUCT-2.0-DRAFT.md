# 微信对话工作台 2.0 功能需求文档

> 历史需求草稿：本文保留需求讨论背景，并非当前功能或验收承诺。实际实现与限制请参阅 [2.0 部署与开发说明](DEVELOPMENT-2.0.md)。

状态：待评审 · 日期：2026-10-27 · 适用范围：平台服务端、Windows 客户端、云端记忆和 MCP

本文定义下一版的产品目标、功能、数据边界和验收方式，供需求评审使用。用户已明确的要求作为本稿约束，其余建议和待确认事项由本次评审决定；评审通过后再进入技术设计和实现。

本轮已明确：平台不内置或统一提供 AI 模型，所有模型由用户自主配置；聊天整理与证据无需人工确认，按周期自动写入 Markdown 记忆；个人 MCP 需要读写 Key，并可由服务端管理和禁用；优先使用 mini PC 上已有的 MySQL、Redis 和 MongoDB，按实际用途接入。

## 1. 产品目标

微信对话工作台通过客户端持续采集用户授权的微信通讯录与聊天记录，在服务端按用户、微信账号和会话组织数据。用户选择需要监听的会话后，服务端持续整理对话，生成周期性 Markdown 记忆、个人画像和联系人关系记忆。用户和授权的外部 AI 可以查阅依据、理解上下文并获得沟通建议。

核心价值是“越聊越懂自己”：系统应从长期真实对话中发现有证据支持的表达习惯、偏好、关系和重要约定，并允许用户核对、修正或移除这些记忆。

产品闭环：

1. 平台管理员开通用户；普通用户登录服务端，创建客户端并下载程序。
2. 用户在自己的电脑上安装客户端，使用该客户端的 `appKey` 和 `appSecret` 注册；客户端在授权后自动发现微信、解析本机通讯录和聊天记录，并加密上传。
3. 用户在服务端按微信账号查看通讯录和会话，将需要长期整理的会话加入监听。
4. 用户配置自己的模型；服务端对监听会话进行历史分析与持续处理，按天、周、月、半年和年自动生成并保存 Markdown 总结，同时整理个人画像和联系人关系记忆。
5. 用户可查看并修订记忆，或为外部 AI 配置个人 MCP 读写 Key，在授权范围内查询、更新记忆和生成聊天建议。

## 2. 范围、术语与角色

### 2.1 范围

| 部分 | 本次需求 |
| --- | --- |
| 平台管理 | 用户、使用统计、平台视角客户端管理、运行与审计信息 |
| 普通用户服务端 | 账号、客户端、微信账号、通讯录、会话、监听、消息、记忆、任务、模型与 MCP 管理 |
| 客户端 | Windows 安装与注册、发现微信、解析通讯录和消息、加密上传、状态与故障处理 |

| 外部接入 | 按用户配置的 MCP 读写 Key 提供会话、消息与记忆查询、授权写入及聊天建议 |

现有的日历、CalDAV、Windows 后台周期整理、旧版客户端配置向导和 SKILL 不是本次新功能的主要范围。是否迁移、保留或下线，见第 17 节；在评审决定之前不默认删除已有用户数据或功能。

| 术语 | 定义 |

| 周期记忆 | 一段会话在一个完整时间周期内的 Markdown 总结及其版本、证据和生成状态 |
| 人物关系记忆 | 描述用户与某联系人或群聊关系的 Markdown 文件及其证据和版本 |
| 个人画像 | 从已授权来源综合整理的用户本人信息和表达习惯 Markdown 文件 |

### 3.3 普通用户首次使用

1. 用户登录服务端，在“客户端管理”新建客户端，填写名称和用途。
2. 服务端生成唯一 `appKey` 和 `appSecret`。页面首次展示 `appSecret`，用户复制或通过受保护的引导方式配置客户端。
3. 用户下载并安装与服务端兼容的 Windows 客户端，填写服务端地址及凭据，完成注册和设备绑定。
4. 客户端展示当前可发现的微信账号、可采集的数据范围和上传目标；用户确认后启动自动采集与上传。
5. 服务端依次出现客户端、微信账号、通讯录和会话；用户可按微信账号查看上传进度与历史覆盖范围。
6. 用户将会话加入监听；系统建立历史分析任务并持续处理后续消息。
7. 用户配置自己的模型后，周期总结和人物记忆自动生成并保存；用户可按需查看来源、修订内容或授权 MCP 读写。

## 4. 管理员功能需求

### 4.1 用户管理

- 管理员可创建普通用户，设置登录名、显示名称、初始状态和配额；可以查询、筛选、编辑、启用或停用用户。
- 登录凭据须安全保存；管理员可发起重置，但不读取用户原密码。首次登录或重置后要求用户设置自己的登录凭据。
- 停用用户后，新的用户登录、客户端注册和上传、分析任务与 MCP 调用应被拒绝或停止；已运行任务的最终提交须再次检查用户状态。恢复用户后，历史数据仍按原权限保留。
- 用户删除应区分“停用”和“永久删除”。永久删除必须显示影响范围，并走明确确认、后台清理和结果记录；备份清理规则单独展示。
- 用户的客户端数、数据容量、消息量、模型调用量和任务并发可按配额限制。超额时提示当前用量、受影响操作及处理方式；不静默丢弃已接收数据。

### 4.2 平台使用统计

- 平台总览按时间范围展示：注册/启用用户、活跃用户、客户端在线/离线/异常数量、已连接微信账号数、接收消息量、已用存储、分析任务数量及成功/失败情况。
- 指标标注统计周期、更新时间、单位及计算口径。客户端在线以最近心跳和失联阈值计算，不将“服务端运行”显示为“客户端在线”。
- 支持按用户、客户端版本、任务类型和日期筛选；允许导出聚合统计，不包含消息正文、联系人明文、模型输入或密钥。
- 若统计依赖异步汇总，应显示最后更新时间；缺失或未完成的统计不显示为零。

### 4.3 平台客户端管理

- 管理员可查看客户端所属用户、名称、注册时间、软件版本、设备标识摘要、最近心跳、接入状态和最近错误类型。
- 可停用异常客户端、终止其当前访问凭据、要求用户重新注册；该操作需记录操作者、对象、时间、原因和结果。
- 管理员不能通过客户端管理页面直接读取 `appSecret` 或该用户的微信聊天内容。
- 平台可配置可下载的客户端版本、适用系统、版本说明和校验信息；下载文件由可信发布流程提供，不把账号数据或凭据打进通用安装包。

## 5. 普通用户账号与客户端管理

### 5.1 账号与登录

- 普通用户使用平台分配的账号登录，登录后只能访问和操作自己的客户端、微信账号、数据、记忆、任务与授权。
- 支持退出、修改密码、会话失效及重置凭据后的旧会话撤销。平台是否开放自主注册、密码找回、多因素认证，见待确认事项。
- Web 管理会话与客户端凭据、MCP 凭据分别管理，避免一个凭据默认获得全部权限。

### 5.2 创建与管理客户端

- 用户可新建客户端，设置名称、备注；系统生成唯一 `appKey` 和随机 `appSecret`，显示服务端地址和安装配置说明。
- `appSecret` 仅在创建或重置时展示一次；列表和接口不得再次返回明文。用户遗失时通过重置生成新凭据，而非找回原值。
- 客户端列表显示注册状态、绑定设备标识、客户端版本、最近心跳、关联微信账号、上传状态、错误和最后成功同步时间。
- 客户端状态至少包括：未注册、已注册在线、已注册离线、异常、已停用；“在线”和“上传成功”分别展示。
- 用户可重命名、停用/启用客户端、重置 `appSecret`、解绑并重新注册。停用应立即拒绝新请求，使已签发的访问令牌失效，并阻止在途任务提交。
- 重置密钥后旧密钥和基于旧密钥的会话失效，客户端需要使用新密钥重新认证；历史微信数据和既有会话归属不因密钥轮换而改变。
- 一个客户端身份默认绑定一台设备实例；同一用户的多台电脑分别创建客户端。设备更换或应用重装通过明确解绑/重新注册处理，避免一个密钥被多个设备无提示复用。
- 用户可从服务端下载客户端安装包，查看版本、支持系统及校验值。客户端启动后可检查版本；是否自动更新及升级策略待确认。

### 5.3 注册、心跳与认证

- 客户端首次填写服务端地址、`appKey` 和 `appSecret` 后发起注册；服务端验证客户端归属、状态及设备绑定，返回受限且有有效期的客户端访问凭据。
- 注册和后续访问通过加密传输；凭据不出现在 URL、日志、错误详情、统计或普通接口响应中。客户端在本机系统提供的安全存储中保存凭据。
- 客户端按配置发送心跳，包含版本、同步阶段及非敏感错误分类。服务端按最后心跳计算在线/离线，支持断线重连和安全续传。
- 对过期、停用或被重置凭据的客户端，服务端返回可识别的认证失败；客户端停止上传并提示用户重新配置，不反复输出密钥或消息正文。

## 6. 微信账号与通讯录管理

### 6.1 微信账号管理

- 客户端自动发现本机已安装微信及其可读取账号；用户可从客户端确认要连接和上传的账号。未检测到微信、未登录、权限不足、数据库密钥失效或版本不兼容时，应分别给出状态和下一步。
- 一个平台用户可关联多个微信账号；一个客户端可关联多个微信账号。每个账号展示可识别的名称、微信标识、来源客户端、首次关联时间、最近同步和数据覆盖情况。
- 数据归属始终包含平台用户 ID 与微信账号 ID。同名账号、同名联系人不得仅凭显示名称合并。
- 微信账号标识应尽量使用稳定的微信侧标识，并记录来源与可信度；账号目录迁移、微信重装或密钥变化不能直接作为新账号或数据重置的唯一判断依据。无法安全判断时要求用户确认归属。
- 多个客户端发现同一个微信账号时，服务端应识别为同一账号的多个数据来源，并以稳定消息身份去重；发生身份冲突时暂停合并并提示用户处理。
- 用户可暂停某微信账号的采集上传、断开来源客户端或归档账号。暂停不等于删除已存数据，删除须走明确的数据删除流程。

### 6.2 通讯录管理

- 客户端解析可读取的联系人、群聊及群成员资料，包含稳定标识、昵称、备注、头像引用、联系人类型、所属微信账号和更新时间；缺失字段保留为空，不臆造。
- 服务端按微信账号展示和搜索通讯录，支持按昵称、备注、标识、联系人/群聊筛选；联系人详情可跳转关联会话、自动生成的关系记忆及来源证据。
- 联系人资料发生变更时更新最新资料并保留必要的变更时间；用户手工备注和人工编辑的关系记忆不被同步资料覆盖。
- 同一个人可能在多个微信账号下具有不同标识。默认不自动合并；如需跨账号合并，应由用户确认关联，合并和撤销关联不得删除原始身份或消息来源。
- 群聊作为独立会话与群体关系管理；可识别群成员时记录真实成员身份，未知成员明确标记，不将群聊所有消息归到单一联系人。
- 联系人从微信通讯录消失、被删除或暂时无法读取时，标记来源状态和最后发现时间；不因此自动删除已上传的历史会话与记忆。

## 7. 客户端解析与加密上传

### 7.1 启动与采集范围

- 首次完成注册并获得用户确认后，客户端自动运行微信发现、账号连接、通讯录及会话目录解析，并按账户采集范围自动解析本机可用聊天记录。
- 本建议方案将“采集/上传范围”和“监听分析范围”分开：已授权微信账号的可读取通讯录与全部可读取会话消息可上传；只有用户在服务端加入监听的会话进入自动分析和记忆生成。用户可在客户端或服务端暂停某账号的采集。
- 因该范围比现有 1.0 的“仅选择后读取”更广，首次开启前必须清楚显示目标账号、上传内容与目标服务端；默认全量或先选范围是重点评审项。
- 客户端对微信原始数据库只读；不修改微信记录、不替用户发送消息。解密与解析失败应保留错误状态，并允许修复后继续，不把失败数据库报告为已完成。
- 解析范围首先支持项目当前 Windows 版微信及已验证的数据库结构；不同微信版本、系统版本、权限要求和多账号支持范围应以实际适配验证为准。macOS、Linux 客户端是否纳入首期待确认。

### 7.2 内容类型与边界

| 类型 | 首期建议处理 | 云端分析与展示 |
| --- | --- | --- |
| 文本、系统消息、撤回记录 | 解析正文、发送者、时间、类型及可用原始内容 | 展示文本和状态；撤回与编辑按来源更新 |
| 群聊 | 解析群会话及可识别的发送者 | 区分群聊、成员和本人，不把未知发送者误认为本人 |
| 引用、链接、文件、名片、位置 | 解析可获得的标题、引用、名称、位置等结构化字段并保留原始记录 | 可搜索解析文本；不可解析部分明确标记 |
| 图片、语音、视频、表情 | 保存消息类型、描述和可读取元数据；附件原文件上传及处理能力待确认 | 不声称已识别图片、转写语音或理解视频，除非对应能力已启用并完成 |
| 数据损坏或未知类型 | 保留可安全读取的标识、类型和原始内容，记录解析错误 | 可查看失败原因，不影响其他可解析消息 |

原始微信数据库、数据库解密密钥、微信登录凭据默认不上传。附件二进制是否上传、压缩、分析及相关空间和费用，需单独评审；聊天文本中本身包含的文件路径或链接作为消息数据处理。

### 7.3 全量、增量与可靠性

- 首次连接对已授权范围执行历史全量读取与上传；客户端展示发现的账号/会话数量、历史时间范围、已完成/待处理量、当前阶段及错误。历史多时允许长时间后台继续，不因用户关闭页面而丢失进度。
- 全量期间也可接收新消息。上传顺序、断点和历史补齐状态应明确区分，不能只因为最新消息已出现就显示“全部历史完成”。
- 后续基于可验证的游标和变更检测增量上传，覆盖新增、修改、撤回和迟到数据。断网、服务端重启和客户端重启后自动重试和续传；重试不得产生重复消息。
- 每条消息应携带平台用户、微信账号、会话、来源设备、来源数据库分片、稳定消息标识、发送者、消息时间、类型、解析版本和同步版本。优先使用可验证的微信消息唯一标识；缺失时使用带来源范围的稳定复合身份并标记可信度。
- 同一个微信账号由多客户端上传相同消息时应幂等合并；如果不同来源共享的标识无法可靠证明相同，保留来源并提示可能重复，不能无依据覆盖。
- 支持分批提交与确认、重试退避、失败队列、限速和用户可见错误。服务端只有在事务持久化成功后才确认该批；客户端以服务端确认位置推进，断点处可安全重复发送。
- 对部分数据库读取失败、永久无法解析的单条消息、损坏附件、磁盘不足、服务端空间满、认证失败分别显示受影响范围和可执行操作；不能一直以“同步成功”掩盖缺口。
- 本机微信消息被删除不自动等同于云端删除。撤回/编辑记录与“永久删除本产品数据”分开处理；是否同步源端删除为待评审项。

### 7.4 账户加密与云端处理

本需求同时要求“账户加密上传”和“云端自动解析、总结”。要让服务端执行分析，分析过程必须能获得明文或在用户可控的可信执行环境中获得解密能力。仅客户端持钥且服务端永远无法解密的严格端到端加密，与普通服务端直接分析不兼容。

**建议评审方案：用户级数据密钥 + 服务端受控解密。**

1. 每个平台注册用户拥有独立的数据加密密钥；客户端在上传前使用该用户密钥加密消息、通讯录及相关附件，传输全程使用 TLS。服务端生成的记忆也按用户密钥加密后持久化，业务数据以密文保存。
2. 客户端加密、服务端解密处理、重加密持久化所需的密钥封装、交换、版本与恢复机制，必须在实现前完成威胁模型及安全设计。密钥的服务端托管/解封能力及其能访问明文的边界必须明确告知用户。
3. 仅用户授权的读取、搜索、MCP 调用和分析任务在所需范围内解密；明文不得写入普通日志、监控指标、错误消息或不受控的临时文件。实际运行时内存与必要的模型输入会接触明文。
4. `appSecret` 只用于客户端身份认证，不能直接作为唯一数据加密密钥；重置客户端凭据不能导致历史数据无法解密。更换设备、服务重启、密钥轮换与用户恢复应有可验证流程。
5. 服务端搜索若依赖索引，应说明索引暴露的信息与加密方式；不能一边声称“服务端无法读取明文”，一边依赖服务端明文索引或明文模型调用。
6. 使用第三方模型时，所选消息、记忆和摘要可能发送给模型提供方；用户需能看到服务地址、数据范围、模型和费用归属，未完成模型配置的任务应保持等待而非假报完成。

具体密钥托管机构、是否支持用户自持密钥/严格端到端加密及密钥丢失时的恢复策略，均在第 18 节列为决策项。不同方案影响云端分析、搜索、恢复和运维能力；用户自主配置模型的访问要求见第 9.2 节。

## 8. 会话管理与监听

### 8.1 会话列表和消息查询

- 会话按微信账号分组，展示会话类型、名称、对应联系人/群聊、最近消息时间、已上传消息数、历史覆盖范围、来源客户端、同步状态和监听状态。
- 支持按名称、备注、微信标识、类型和监听状态搜索/筛选；会话和消息读取均按平台用户及微信账号隔离。
- 会话详情支持按关键词、时间范围、消息类型和发送者查询；消息按时间稳定排序，保留发送者、来源和可用的引用/原始元数据。
- 分页或游标读取期间如有增量消息、更新或删除，应通过稳定排序与版本提示避免漏读/重复；客户端和调用方可依据消息 ID 去重。
- 可导出当前筛选结果或指定完整范围的 JSON / Markdown，并明确时间范围和消息数量；导出属于当前用户主动操作，保留消息正文的字面含义，避免执行消息中的 HTML 或脚本。

### 8.2 监听生命周期

监听状态至少包括：未监听、等待数据/模型、历史分析中、持续监听中、已暂停、失败待处理、已移出。列表及详情展示每个阶段的进度、最近成功时间和错误原因。

| 操作 | 预期行为 |
| --- | --- |
| 加入监听 | 原子记录监听关系；创建历史分析任务和后续周期调度，立即尝试执行 |
| 历史尚未上传完成 | 已收到的数据可分析，但状态显示“历史补齐中”；后续上传到达后补充分析和重算受影响周期 |
| 暂停监听 | 停止新分析并取消或阻止在途任务提交；保留已保存的消息和记忆，可继续浏览 |
| 恢复监听 | 从上次成功处理位置追补暂停期间的数据，受影响周期重新评估 |
| 移出监听 | 停止分析与后续记忆更新；已保存消息和记忆默认保留，是否允许 MCP 继续读取由授权范围决定 |
| 永久删除会话数据 | 明确确认后清理消息、引用和相关派生记忆，阻止仍在运行的任务重新写回；后续重新上传行为须说明 |

建议首次监听后从当前服务端已接收的完整历史开始分析，并在数据继续上传时增量补齐。历史量很大时通过后台队列限并发，优先处理近期消息，展示积压与范围，不静默截断。是否默认回溯全部历史及模型费用上限需评审。

监听是服务端决定的分析范围；客户端即使暂时离线，服务端仍可处理已上传记录。客户端离线期间的新微信消息只有在客户端恢复并上传后才能被分析。

## 9. 云端分析、模型与自动化

### 9.1 处理流程

1. 接收并校验客户端上传，完成认证、账户归属检查、数据解密能力校验、去重和持久化。
2. 对监听会话识别新数据或受影响历史范围，创建可追踪的分析任务；非监听会话仅按采集授权存储与查询，不自动生成记忆。
3. 清理和规范消息结构，关联微信账号、会话、发送者及时间；遇到无法解析的类型保留状态，不伪造文本。
4. 按时间排序、模型输入预算和上下文限制拆分，逐段提取事实、线索与来源证据；长历史完整处理，不能只拿最近消息冒充全部历史。
5. 合并分段结果，生成对应周期 Markdown、个人画像和联系人关系记忆。自动记录可回查的消息证据及不确定性，无需用户逐条确认。
6. 生成完成后直接按所属周期保存 Markdown 记忆并更新相关画像与关系记忆，同时提交来源范围、处理版本和任务结果；失败或取消不将半成品标为成功。
7. 用户可随时查看、修订或删除记忆，但这些操作不作为自动生成和保存的前置条件。后续分析保留人工内容，并基于新增证据自动产生新版本。

### 9.2 模型配置与调用

- 平台不内置模型、不向用户统一提供默认模型或推理服务。每个普通用户在服务端自主配置模型服务地址、模型名称、认证凭据（如服务需要）及运行参数；可根据任务选择自己已配置的模型。
- 用户可新增、编辑、删除、启停和测试自己的模型配置；测试连接只发送测试内容，不发送聊天。模型密钥加密保存，设置页面不回显明文；管理员不读取用户模型密钥。
- 用户配置的模型可以位于其自有环境或第三方服务，但必须能从服务端实际运行环境访问；服务端不会自动安装或启动模型。用户负责对应服务的可用性、额度及费用。
- 模型未配置或被停用时，监听与同步可正常保存；自动分析任务显示“等待配置模型”，配置可用模型后可恢复执行并补跑，不使用平台备用模型。
- 每次分析任务记录模型标识、提示模板/解析规则版本、消息范围、消息数量、生成时间、状态及可获得的用量；普通运营日志不记录模型输入、输出正文或凭据。
- 当模型未配置、连接失败、额度不足、响应超时或输出结构无效时，任务进入可见的等待/失败状态，支持退避重试、手动重试和取消；不得标记完成。
- 同一会话、周期、数据版本、规则版本与模型配置的重复任务应幂等；内容没有变化时可复用结果。规则或模型升级是否默认重算所有历史由用户/管理员策略决定，不能隐式大量消耗额度。
- 支持并发控制、按用户公平调度、可观察的排队进度与资源限额；网络重试必须有上限和可恢复状态。
- 聊天内容、引用、附件和记忆均作为待分析的数据，而不是模型或系统指令。模型不执行其中要求泄露数据、改变权限或调用外部工具的指令。

### 9.3 首次监听与持续任务

- 首次加入监听后立即创建历史补齐任务；若没有可分析消息则显示“等待消息”，已有消息不要求等待下一个自然周期才开始初次分析。
- 新消息到达后触发增量提取与记忆更新；周期总结在对应自然周期结束后自动生成并保存，无需人工确认。对尚未结束的周期，可提供标注为“进行中”的临时摘要，不与正式周期总结混淆。
- 对历史上传未完成、消息迟到、撤回、编辑或解析规则修正，系统识别受影响会话和周期，生成新的版本；不重复生成同一输入版本，也不无提示覆盖人工编辑。
- 删除、停用账号、移出监听或权限撤销时，取消排队任务；运行中的任务在读取、外部调用和写入前再次检查授权和数据版本。已发出的外部模型请求无法保证被撤回，应在操作结果中如实标注。

## 10. 五种周期总结

### 10.1 时间定义

建议默认使用北京时间 `Asia/Shanghai`，以自然周期为准；时间范围统一采用“开始包含、结束不包含”，并保存时区和区间边界。

| 周期 | 范围与触发规则 | 示例 |
| --- | --- | --- |
| 日 | 本地自然日结束后生成 | 2026-10-27 00:00 至 2026-10-28 00:00 |
| 周 | 周一 00:00 至下周一 00:00，周期结束后生成 | 2026-10-26 至 2026-11-02 |
| 月 | 当月 1 日 00:00 至下月 1 日 00:00 | 2026-10-01 至 2026-11-01 |
| 半年 | 每年 1 月 1 日至 7 月 1 日、7 月 1 日至下一年 1 月 1 日 | 2026 上半年为 01-01 至 07-01 |
| 年 | 每年 1 月 1 日 00:00 至下一年 1 月 1 日 00:00 | 2026-01-01 至 2027-01-01 |

周期、时区、生成时间、消息范围和历史是否完整都应显示在页面与文件元数据中。跨时区用户是否可自行配置时区及变更后的重算策略待确认；不能用固定秒数代替自然月或自然半年。

### 10.2 周期任务规则

- 日、周、月、半年、年默认均启用并在周期结束后自动保存 Markdown 记忆，无需人工确认；用户可对所有监听会话或单个会话分别停用或重新启用某个周期。
- 每个周期结束后，系统自动为存在有效消息的监听会话创建任务。无消息的周期不产生虚构摘要，界面显示“无消息”或“无记录”。
- 服务不可用或模型失败后，任务恢复时应补跑缺失的已完成周期；每一周期有唯一任务键和版本，避免重复文件与重复计费。
- 长周期可以汇总日/周/月成果以控制成本，但必须保留可追溯到原始消息的证据；来源摘要缺失或过期时，应补齐或明确标注覆盖缺口。
- 迟到消息或被修改/撤回消息到达后，重新评估其所属日、周、月、半年及年，并按配置重算受到影响的文件及个人/关系记忆。重新生成不得丢失用户手工修改。
- 用户可以手动触发某会话、某周期或指定历史范围的重算，执行前显示目标范围、已有版本与预计调用范围；任务支持进度、取消、失败详情与重试。
- 是否限制历史补跑、最大并发和数据保留期由配额和产品策略控制，并在用户界面明确显示；默认初始历史策略见第 18 节。

### 10.3 周期 Markdown 内容

每份周期总结至少包含：

- 所属平台用户、微信账号、会话、周期、时区、时间范围、生成时间、版本和消息覆盖情况。
- 对话概览、重要事实与主题、决定/约定、待办与未解决事项、关系或沟通变化，以及仍需确认的问题。
- 本人表达方式或偏好变化、联系人或群聊相关变化；区分用户明确表达、对话事实和模型推测。
- 对关键结论提供证据链接或引用：微信账号、会话、消息 ID、发送者和时间；证据失效或来源不可访问时显示原因。
- 自动收集并存储依据，无需用户审核；可选保留用户批注和人工修正。周期中没有证据支持的推测应标记为推测，不当作确定事实。

## 11. 个人画像与人物关系 Markdown

### 11.1 个人画像

- 每个平台注册用户拥有一份可持续维护的个人画像 Markdown，来源于其授权分析的监听会话；可按微信账号筛选来源，避免将不同微信身份的数据混淆。
- 本人画像自动提取只能将已可靠识别为“本人”的发言作为本人直接证据；对方对用户的评价须标记为“对方观点”，不能直接当作用户自述事实。
- 画像可包含：基本信息、表达风格、兴趣与偏好、长期目标、习惯、价值观或边界、重要变化及有待进一步了解的内容；不把模型推断写成心理诊断或既定人格标签。
- 画像由系统依据已授权记录自动更新并保存，无需用户确认；用户可自行创建、阅读、编辑或删除条目，查看产生依据、更新时间和版本。人工撰写内容与自动生成内容分别标记。
- 当某个会话停止授权或其消息被删除时，相关自动结论失去来源后应重新评估；没有其他有效依据的自动结论不再作为已知事实用于建议。用户主动编写的内容按用户选择保留或删除。

### 11.2 联系人与群聊关系记忆

- 每个已监听私聊的联系人可有独立关系 Markdown；记录联系人基础资料、双方关系背景、沟通偏好、共同经历、重要约定、明确边界、待办和时间线。
- 群聊维护独立的群体记忆，描述共同目标、讨论、决定与待办。可识别的群成员关系与个人记忆按成员分别组织，不将群体结论写成某个人的事实。
- 记忆默认以“平台用户 + 微信账号 + 联系人/群聊稳定标识”为归属；跨微信账号合并同一联系人需用户确认，并保留每个原始身份及证据。
- AI 自动提取的事实和推测直接保存并标记来源与不确定性，无需人工确认；用户可按需调整、合并、编辑或删除。矛盾结论并列显示来源和时间，不自动以最新文本覆盖既有事实。
- 同一消息可支持多条记忆，但每条自动记忆都应关联可访问的真实证据。删除或撤销来源权限后，相关记忆版本需标记失效或重新生成。

### 11.3 文件组织、编辑与版本

以下为逻辑路径示例，具体存储介质可在技术设计中决定；不能因选择数据库存储而让用户失去 Markdown 查看和导出能力。

```text
用户空间/
  profile/me.md
  wechat/{微信账号标识}/
    contacts/{联系人标识}/relationship.md
    groups/{群聊标识}/relationship.md
    sessions/{会话标识}/periods/day/2026-10-27.md
    sessions/{会话标识}/periods/week/2026-W44.md
    sessions/{会话标识}/periods/month/2026-10.md
    sessions/{会话标识}/periods/half-year/2026-H2.md
    sessions/{会话标识}/periods/year/2026.md
```

- 文件支持 Markdown 预览、源码编辑、单文件及范围导出；输出为 UTF-8。逻辑 ID 不直接使用未经处理的显示名称作为文件路径。
- 文件及其版本具有稳定 ID、所属账号/会话、内容来源、消息范围、时区、模型、状态、生成时间、最后修改时间和版本号。
- 用户人工编辑与后台生成并发时使用版本检查，自动生成内容和人工内容分别保存。发生冲突时保留双方内容与新版本并提示处理，不静默覆盖人工内容，也不把人工确认作为生成结果入库的条件。
- 历史版本、证据和人工修改受同样的账户隔离与加密保护。删除、导出和恢复的范围及保留周期应可见；物理删除策略见第 14 节。
- Markdown 中来自聊天或模型的内容按不可信文本处理，预览不得执行脚本；外部链接和图片加载策略应避免意外泄露用户信息。

## 12. MCP 与聊天建议

### 12.1 授权和接入

- 服务端提供可由外部 AI 连接的 MCP 接入，支持远程连接；为不支持远程连接的客户端是否提供本地 stdio 桥接，由兼容性评审决定。
- 用户可为每个外部 AI 客户端创建独立的个人 MCP 接入配置，分别生成读取 Key 和写入 Key；两种 Key、客户端 `appKey` / `appSecret` 和 Web 登录凭据互不复用。
- 用户可查看 Key 名称、权限、绑定账号/会话范围、状态、创建时间、最近使用时间，并随时启用、禁用、撤销或重新生成；密钥明文只在创建或重新生成时展示一次。
- 服务端管理页面支持管理员按用户查看 Key 的标识、权限与状态并随时禁用或撤销；管理员操作有审计记录，不能通过管理页面读取密钥明文或聊天正文。用户也可管理自己的 Key。
- 读取范围至少支持限制微信账号和会话。建议默认仅包含监听会话，用户可以显式授权其他已上传会话；未授权会话即使知道 ID 也不能读取。
- 读取 Key 用于授权范围内的会话、消息、通讯录、记忆和任务查询；写入 Key 用于授权范围内的记忆写入和会话监听管理。可分别设置能力和微信账号/会话范围；仅持读取 Key 不得执行写操作，写入 Key 不自动取得未授权的读取权限。
- 建议生成使用用户自行配置的模型及其额度；MCP 不继承客户端上传凭据或管理员权限。无可用模型时返回明确的等待配置状态。
- 每次请求按 Key 类型、状态、平台用户、微信账号、会话和能力范围校验；禁用或撤销后立即拒绝新请求，运行中的写入和生成任务提交前再次检查权限，不发布越权结果。
- 写 Key 可按能力分别允许记忆创建/修改和监听管理；写操作记录操作者、目标、时间、结果与版本，重复请求应幂等，涉及已有文件时检查版本。永久删除能力是否开放给 MCP 另行评审；写 Key 不得修改平台账号、其他用户数据、客户端密钥、MCP Key、模型凭据或任意服务端文件，也不能发送微信消息。
- MCP 接入页展示服务地址、客户端配置示例、授权范围及连接状态；配置示例默认不展示明文凭据，用户主动选择后再复制。
- 审计记录调用时间、授权身份、工具名、请求范围、结果和错误分类；不记录消息全文、提示词正文或明文凭据。分页稳定性与查询数据版本应暴露给调用方。

### 12.2 工具能力

| 能力 | 输入与范围 | 结果与约束 |
| --- | --- | --- |
| 查询状态 | 当前授权用户 | 服务可用性、可访问微信账号、数据同步时间；不返回密钥 |
| 查询微信账号与会话 | 关键词、微信账号、分页 | 返回授权范围内账号/会话及监听状态 |
| 查询聊天消息 | 微信账号、会话、时间范围、分页 | 返回来源、发送者、时间、类型和内容；默认仅授权范围 |
| 搜索聊天消息 | 会话、关键词、时间及类型 | 返回匹配记录与稳定消息 ID，不跨用户搜索 |
| 查询通讯录 | 微信账号、联系人关键词、分页 | 返回授权范围内联系人及会话关联；是否单独开放完整通讯录待确认 |
| 读取周期与人物记忆 | 读取 Key、会话/联系人、周期、时间、版本 | 返回用户可访问的 Markdown 和来源；区分有依据的内容与推测，无需人工确认 |
| 新建或更新记忆 | 写入 Key、目标文件、内容、预期版本 | 在授权范围内创建或更新 Markdown，保留来源、写入者和版本；冲突不覆盖已有内容 |
| 管理监听会话 | 写入 Key、微信账号、会话及操作 | 在授权范围内添加、暂停、恢复或移出监听，并按监听生命周期处理任务 |
| 生成聊天建议 | 会话、当前情境、目标及可选最新消息范围 | 返回对话理解、风险提示、多个候选回复和依据；用户自行选择和发送 |
| 查询分析任务 | 授权会话及任务 ID | 返回进度、完成状态、时间和错误分类；不提供跨账户任务 |
| 导出聊天或记忆 | 授权范围、格式、分页/时间 | 返回内容或受控下载，不向任意服务器路径写文件 |

“聊天恢复建议”暂按“聊天回复建议，并可帮助恢复中断的话题或缓和关系”理解，相关输出需基于已授权记录并说明不确定性；是否同时要求找回微信中已经删除或丢失的聊天记录，需要评审确认。系统不承诺还原本机及服务端均不存在的数据。

### 12.3 建议内容与控制

- 用户输入当前情境、沟通目标和语气；系统结合最近消息、会话备注、双方自动生成或人工编辑的记忆及相关周期总结，生成对话分析与多条可编辑建议。
- 自动记忆不需要人工确认即可使用；对缺乏直接依据的推测应标明不确定性，过期或已撤销证据不能作为有效依据。需要时引用时间、发送者和消息来源，信息不足时说明。
- 建议只能复制或返回给调用方；不自动发送、登录微信、执行聊天内指令或替用户作出承诺。外部 AI 是否保留或使用读取数据由其自身处理，授权页面应告知调用范围。

## 13. 数据模型与状态

### 13.1 核心对象

| 对象 | 关键字段与关系 |
| --- | --- |
| 平台用户 | 用户 ID、登录标识、角色、状态、配额、创建/停用时间、加密密钥版本 |
| 客户端 | 客户端 ID、所属用户、名称、`appKey`、密钥校验信息、设备绑定、状态、版本、心跳 |
| 微信账号 | 平台用户 ID、微信账号稳定标识、显示资料、来源客户端关联、同步和采集状态 |
| 联系人/群成员 | 所属用户与微信账号、微信侧标识、类型、展示资料、来源、更新时间 |
| 会话 | 所属用户与微信账号、会话标识、类型、联系人/群聊、监听状态、最近同步 |
| 消息 | 用户、微信账号、会话、稳定消息 ID、来源集合、发送者、时间、类型、内容及变更版本 |
| 同步批次/游标 | 客户端、微信账号、会话或分片、范围、状态、确认位置、错误、上传版本 |
| 监听关系 | 用户、微信账号、会话、状态、开始/暂停时间、历史分析策略、周期配置 |
| 分析任务 | 用户、会话、任务类型、周期区间、输入版本、模型/规则版本、状态、重试和用量 |
| Markdown 记忆 | 用户、类型、微信账号、会话/联系人、逻辑路径、版本、内容状态、来源和更新时间 |
| 证据引用 | 记忆版本、用户、微信账号、会话、消息 ID、发送者、消息时间及有效性 |
| MCP 授权 | 用户、名称、读取 Key / 写入 Key 的标识和校验信息、能力范围、微信账号/会话范围、状态和时间 |
| 审计事件 | 操作者、对象、操作、时间、结果、必要的错误分类；不保存明文敏感内容 |

所有包含业务数据的读取、写入、异步任务和缓存都必须带用户归属；微信账号、联系人、会话和消息必须使用其完整作用域，不能仅靠名称或裸会话 ID 查找。

### 13.2 状态与并发约束

- 客户端注册、停用、重置和消息写入要检查当前授权版本；不得在停用后继续接受旧凭据。
- 同步批次以稳定身份幂等提交；重复批次不会增加消息数，冲突或更新产生可审计版本，不以到达顺序盲目覆盖更可信数据。
- 监听任务和周期任务使用唯一任务键及租约/锁，防止多工作进程重复执行；提交时再次核对监听、用户权限及输入版本。
- 分析结果和记忆更新按版本原子发布；任务取消、权限撤销或输入变化不得发布过期成果。人工编辑冲突由用户合并。
- 所有状态变更展示时间及原因；后台失败要有可查看、可重试、可终止的路径。

## 14. 隐私、删除、备份与审计

### 14.1 隔离与授权

- 平台用户数据相互隔离；客户端只可上传所属用户数据，MCP 按只读 Key 或全部权限 Key 的授权范围访问和操作数据；平台管理员默认不看用户内容。
- 客户端权限最小化：只访问所选本机微信数据和运行所需资源；不修改微信数据库，不扫描无关个人文件。
- 用户应能随时查看已授权的微信账号、客户端、监听会话、模型服务和 MCP 客户端，并暂停或撤销后续访问。
- 客户端、服务端、浏览器、模型服务及备份各自的明文访问边界和加密状态应在产品与部署文档中准确说明。

### 14.2 删除与恢复

- “暂停采集”“移出监听”“停用客户端”“删除会话”“删除微信账号”“注销平台账号”分别说明对消息、通讯录、记忆、任务、授权和备份的影响，不将状态变更误称为物理删除。
- 永久删除前展示待删除范围和不可逆影响并要求用户确认；完成后记录进度和结果。对已经导出的文件、第三方 AI 或模型服务已接收的数据，不能承诺自动撤回。
- 数据删除应联动相关分析任务、索引、缓存、密钥封装、证据、记忆派生内容与备份生命周期；若某部分需延迟清理，应明确其保留期限和可见状态。
- 若客户端仍对被删除会话启用上传，系统需提供明确策略，避免数据被不知情地立即重新上传。建议删除时可选“同时停止该会话后续采集”，具体默认待确认。
- 支持用户导出自己的会话、通讯录和 Markdown 记忆，并说明格式及覆盖范围；不在普通导出包中包含客户端认证密钥或服务端主密钥。

### 14.3 备份与审计

- 备份覆盖加密数据、必要索引、元数据及密钥恢复材料；提供定期备份、恢复验证与恢复失败告警。数据库与备份同时丢失时不能承诺找回。
- 跨 MySQL 与 MongoDB 的备份须记录一致性检查点及版本关联；恢复时校验记忆版本指针与内容并修复未完成任务。Redis 的缓存、锁和调度通知应可重建，不作为备份中唯一的数据或任务副本。
- 用户可查看自己的登录、客户端注册/停用、上传异常、监听变更、模型使用及 MCP 授权/调用记录；管理员可查看平台级管理操作。
- 日志、错误和监控避免包含聊天正文、通讯录明文、模型输入输出、密码、密钥或令牌；排障信息按角色最小化展示。
- 用户、客户端、微信账号、消息和记忆的默认保留期限、备份留存及审计保留期待评审；文档不预先假设某地区的法律要求或合规认证。

## 15. 非功能需求与可观测性

### 15.1 可靠性

- 服务端重启、WSLC 容器重建和客户端重启后，已接收的消息、用户配置、监听状态、任务进度和自动保存的记忆版本保持一致。
- 持久化提交、批次确认、任务租约、重试与恢复须可测试；断网和重复上传不造成消息丢失或重复。
- 平台应区分客户端离线、采集失败、上传失败、云端待处理、模型失败和已完成；用户能看到阻塞原因和最后成功时间。
- 长任务可查询进度与取消；服务端后台任务不依赖浏览器页面保持打开。
- 容量、消息吞吐、任务并发和恢复时间目标应在明确预计用户规模、单用户历史量及部署资源后制定，并基于真实数据规模压测。首期不能以未验证数字作为交付承诺。

### 15.2 体验与可用性

- 管理端区分管理员和普通用户导航；关键状态同时用文字和视觉标识表达，空列表提供下一步操作。
- 所有新增表单有可见标签、错误提示和键盘操作；长文本、长名称、移动端及窄屏不应遮挡关键操作。
- 客户端显示账号连接、授权范围、采集/上传进度、历史覆盖、最近成功时间和错误处理方式；服务端展示同一账号的最终接收和分析状态。
- Markdown 内容可阅读、编辑、搜索、复制和导出；生成中的内容与已发布版本明确区分。

### 15.3 可部署与运维

- 服务端支持容器化部署、外部配置和持久化数据；本地预览可使用 WSLC，服务启动时检查数据库、密钥、模型服务配置与必要依赖。
- 提供健康检查和只包含非敏感信息的运行指标；支持管理员看到队列积压、失败率、存储和客户端在线状况。
- 客户端安装包包含运行必需依赖及清晰的安装、卸载、升级说明；卸载、停用和删除云端数据的行为彼此区分。
- 开发、测试和生产环境使用独立的用户数据、凭据与模型配置；演示数据不能混入用户账户。

### 15.4 mini PC 数据库接入方案

mini PC 已有 MySQL、Redis 和 MongoDB。建议按以下职责接入，复用现有实例，实际地址、版本、账户权限、可用容量和网络连通性在实施前核实。连接配置由部署环境提供；本次需求评审不修改现有数据库或连接数据。

| 组件 | 建议用途 | 数据持久化与边界 |
| --- | --- | --- |
| MySQL | 用户、客户端、微信账号、通讯录、会话、消息加密内容、监听状态、授权、同步游标、任务状态、审计及记忆版本元数据 | 核心业务数据、授权和任务状态的持久化来源；事务保护游标、幂等和版本发布 |
| MongoDB | 周期 Markdown、个人画像、联系人关系记忆及其不可变内容版本；需要保留的结构化分析结果 | 保存用户加密后的文档内容及关联标识；Markdown 仍可在页面查看、编辑和导出 |
| Redis | 缓存、任务唤醒、限流和短期租约等临时状态 | 仅用于加速和协作；不能作为消息、记忆、授权或任务进度的唯一副本 |

- 仅创建项目需要的独立数据库、集合、前缀和低权限访问账号；不能覆盖或删除 mini PC 上其他应用已有的数据。数据库凭据从安全配置加载，不写入仓库、安装包或日志。
- MySQL 管理记忆的归属、版本状态和已发布内容指针；MongoDB 存放对应的加密内容。先写入可重复识别的不可变文档版本，再通过 MySQL 事务发布指针与任务结果；仅指针指向的完整版本对外可见。
- MySQL 与 MongoDB 的写入不假设存在跨数据库原子事务。中断时允许安全重试、对账和清理已确认的孤立版本；不存在的内容不得被标记为成功发布。用户编辑和 MCP 写入同样遵循版本检查。
- Redis 故障时不丢失已接收消息或任务状态；依赖 Redis 的调度和缓存可暂停或降级，恢复后依据 MySQL 持久状态重建并继续处理。MySQL 或 MongoDB 不可用时，相关写入和读取返回清晰错误，不能伪装成功。
- 账户加密、访问控制、连接安全、健康检查、容量和备份恢复覆盖三个组件；涉及聊天、通讯录或记忆的明文不得作为 Redis 缓存或日志的默认内容。是否最终同时采用三个组件，以详细设计中验证的实际需求为准。

| A28 | 从现有 SQLite 迁移 | 映射用户归属并校验消息、会话和记忆数量；迁移可重试，失败可回退且不覆盖其他数据库的数据 |

## 17. 现有项目差异与迁移要求

### 17.1 当前已有能力

以仓库现有 1.0 规格和客户端/服务端实现为基线：

- Windows 客户端已具备本机微信数据库只读解析、联系人和已选会话读取、部分非文本记录解析。
- 现有本机工作台以用户主动选择会话作为读取/分析边界；现有云端上传按工作台会话上传，使用静态上传和读取 token。
- 服务端已有 SQLite 消息持久化、按凭据隔离的只读 API、只读 MCP 以及只读管理台；管理员/普通用户体系、客户端 `appKey` / `appSecret` 管理和云端自动记忆尚未作为现有能力完成。
- 现有知识库、本人画像、日/周/月整理、回复建议及日历能力主要在客户端执行；不能把它们直接视作云端五周期 Markdown 记忆已实现。
- 项目当前提供 WSLC 本地部署和服务端数据卷；已有客户端设置、服务端数据和用户手工知识需要纳入迁移设计。

### 17.2 升级与兼容

- 升级前识别旧版本、现有服务端账户/静态 token、微信账号绑定、会话、消息、备注、知识、摘要、日历、客户端设置和 MCP 配置。
- 提供可预演的迁移方案：展示来源、目标用户、待迁移数量、冲突及备份位置；由用户或管理员确认目标归属后执行，避免旧账号被错误合并到新平台用户。
- 迁移前做一致性备份；迁移过程可恢复、可重试、可校验，失败时保留旧数据和日志，不能静默覆盖用户手工内容。
- 将现有 SQLite 中的会话、消息、备注和上下文迁移到 MySQL，将需要长期维护的 Markdown 记忆版本迁移到 MongoDB；迁移完成前执行数量、消息身份、版本引用和用户归属核对，并保留原数据库供回退。Redis 状态在新系统启动后按持久数据重建。
- 为历史消息建立新用户/微信账号/会话作用域及稳定身份映射；无法确定微信账号、消息唯一身份或跨客户端对应关系时列入待确认清单。
- 旧版静态上传/读取 token、MCP 连接与客户端同步方式的兼容期、切换步骤及撤销时点需由发布方案规定；新旧凭据权限不能意外扩大。
- 已有人物知识与总结应保留原文、证据、人工内容和历史状态；转换为 Markdown 时已忽略内容维持忽略，历史确认状态只作来源元数据，不成为新记忆自动保存的前置条件，也不凭空补充缺失证据。
- 原有日历、CalDAV、自动化、图片查看、SKILL 和客户端配置功能的保留、迁移或退役范围需单独评审并明确用户可见的变化；本草案不默认删除。

## 19. 建议交付顺序

以下是为降低迁移和联调风险建议的交付顺序，不代表排期或已批准范围。

1. **基础账户与客户端接入**：用户/角色、客户端凭据、注册绑定、Windows 客户端下载和状态、加密方案及数据隔离。
2. **微信与数据同步**：接入 mini PC 上必要的 MySQL、MongoDB 和 Redis，多微信账号、通讯录、会话、历史与增量上传、断点恢复、消息查询和运维统计。
3. **监听与记忆闭环**：用户自主配置模型、服务端监听、历史补齐、任务调度、五类周期 Markdown 自动保存、本人画像和联系人关系记忆。
4. **外部 AI 与运营完善**：个人 MCP 读写 Key 管理与建议、客户端/任务审计、跨数据库备份恢复、旧数据迁移、配额和运营配置。

每一阶段都应具备相应的隔离、授权、错误处理、重启恢复与验收；具体拆分和上线顺序以评审结论为准。
