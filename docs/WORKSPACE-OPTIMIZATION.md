# 监听工作区与增量同步

本文件描述监听工作区与增量同步实现。v2.0.10 起，同一微信的多个设备使用统一会话池；部署状态以当前环境的运行版本和部署验证报告为准。

## 同步策略

`helper/incremental_sync.py` 管理每个微信账号、服务端地址和 appKey 对应的独立断点。`sync-progress.bin` 使用 Windows DPAPI 保存，不上传数据库路径、数据库密钥或本地快照指纹。

服务端保留按客户端和本机数据源隔离的原始记录与游标。同一平台注册用户下，微信账号标识完全一致时，对外统一显示为一个微信账号；相同微信联系人或群聊统一为一个会话和监听。会话池按微信服务端消息标识去重；缺少可靠标识时保留各设备记录，不按正文猜测是否重复。不同用户、不同微信号或微信账号标识缺失的数据源不会自动合并。原始设备记录、历史记忆与已有任务保留；分析读取会话池，等待各来源完成历史同步后再从早到近处理。新加入的来源需要支持历史完成确认的 v2.0.9 客户端；旧客户端不会自动发送该确认。

- 首次同步先发送每个普通消息分片的最近最多 100 条记录，让近期对话先可用；较早历史使用单独的 `history_after` / `history_until` 断点在后台补齐。服务端的最高消息游标不代表历史已经补齐。
- 无重点对象时，普通轮次最多读取 1000 条消息；按会话轮转，单分片限量处理。新消息和历史补齐都有机会执行，大会话不会一次占住整个采集循环。实际吞吐取决于微信快照、网络和服务端。
- 通讯录、会话预览按对象指纹发送差异。没有变化的分片跳过读取；分片变化时检查末尾 100 个本地 ID 范围，对实际变化的记录发送加密批次。只在服务端确认后记录消息指纹与断点，失败后安全重试。
- 每 5 分钟与服务端游标对账，并重发目录以恢复服务端重建或回滚后的缺失数据。正常对账中的相同消息不会重传。旧版客户端的既有服务端游标继续有效。
- 末尾重叠范围以外的旧记录修订，需调用现有完整重传能力；普通增量不会声称扫描了全部历史。微信端删除记录或移出采集范围不会删除服务端历史。
- 本地发送者映射按分片快照复用；账号切换清空缓存，不混用同名联系人的信息。

### 重点对象同步

服务端已开启监听的通讯录对象是重点对象。同一微信账号的各设备共享重点对象列表；客户端每轮取得名单，与本机授权范围取交集后优先处理。新增或取消监听在后续轮次生效，不扩大联系人或群聊的上传范围。旧服务端不支持该接口、网络失败或响应异常时，客户端回退到原有普通同步策略，并在后续轮次重新获取列表。

紧凑客户端以 10 秒为重点对象轮次的目标间隔，按本轮开始时间计算等待；无重点对象时保持原有的轮次结束后等待 10 秒。重点对象和其他对象同时存在时，重点对象单独使用最多 600 条的额度，普通对象保留原有最多 1000 条额度，两组各自轮换会话，防止历史补齐挤占另一组。重点与普通处理分别以本轮开始后约 6 秒和 9 秒为协作式让出目标，已开始的数据库操作或网络请求仍需完成。实际间隔会受数据库解密、网络、超时、监听对象数量和处理积压影响，不能保证所有对象都在严格 10 秒内上传；完整同步仍按原有逻辑执行。

## 服务端读写边界

`platform_service.py` 继续集中负责上传校验、用户隔离、监听、记忆版本与 MCP 权限。`platform_workspace.py` 提供监听工作区的读取接口与通讯录添加监听操作，不改变原有 MCP 的授权条件。

| 接口 | 用途 |
| --- | --- |
| `GET /api/v2/workspace/contacts` | 默认监听对象；`contact_type=person/group` 分类，`scope=all` 搜索全部通讯录，支持账号、关键词和分页 |
| `POST /api/v2/workspace/contacts/{id}/listener` | 添加或移出监听；没有聊天会话的通讯录对象会先创建对应会话 |
| `GET /api/v2/sessions/{id}/messages` | `before` / `after` 稳定游标，`count=false` 省去历史总数统计；保留旧 offset 接口 |
| `GET /api/v2/workspace/memories` | 返回个人及监听会话的目录元数据，不读取 MongoDB 正文 |
| `GET /api/v2/workspace/analysis` | 分页返回监听对象的分析进度、状态汇总和最多 10 条失败详情 |

会话列表的消息数改为当前分页的一次分组查询。Web 记忆列表直接在 SQL 分页；目录仅对监听对象解密名称，正文点击后才读取。目录元数据上限 50000 条，达到上限会明确提示；不将姓名或聊天正文写入明文搜索索引。全部通讯录的关键词搜索仍需解密当前用户的目录元数据。

上传相同清单不再重复加密和更新每一行。历史监听入队先在 SQL 按上海自然日去重，再批量读取既有任务，避免逐条历史消息计算周期、逐个任务查询。消息更新后延后至少 45 秒整理，同一会话、周期的变更合并到原任务；未结束的周期仍等待结束后 2 分钟。后台租约、修订检查、重试退避和人工记忆保护继续生效。没有删除或跳过既有历史分析任务。

## 页面模块

`platform.js` 保留登录、公共组件与路由；`workspace.js` / `workspace.css` 实现四个工作区页面。

- 通讯录默认监听列表，顶部添加监听弹窗支持搜索所有通讯录、分类和分页。
- 会话与消息左侧分页加载监听对象，右侧首次加载最新 50 条。更早历史向上加载，运行中每 5 秒请求新消息游标并追加，保留已有消息与滚动位置。
- 记忆目录按个人、对象备注和记忆类型分层，按展开动作加载文件节点。右侧默认 Markdown 预览；编辑工具栏、源码、预览切换、保存冲突提示、未保存修改保护、版本历史和下载独立提供。
- 自动分析按对象汇总状态、失败任务单独处理，进度每 10 秒更新。模型未配置与未结束周期有独立说明。
- Markdown 解析与清理组件随站点本地分发，锁定版本及完整性来源见 `backend/static/vendor/provenance.json`，许可与文件一同保存。预览不执行 Markdown 内的脚本，不加载远程图片。
- 静态资源按内容版本缓存；HTML 和业务接口保持不缓存。

## 验证

`tests/test_incremental_sync.py` 验证近期优先、1000 条以上历史补齐、进程重建后续传、空闲轮次零同步批次、新消息与修订消息、上传失败重试及服务端数据回滚后的对账恢复。

`tests/test_workspace.py` 验证默认监听过滤、通讯录类型、无历史的联系人添加监听、跨用户拒绝、稳定消息游标、目录不读正文、列表统计查询数量、清单去重与分析汇总。

浏览器使用独立 SQLite、内存文档存储和合成消息验证添加监听、125 条历史分三页加载、Markdown 编辑保存和脚本清理、四页 390px 布局。发布部署另外检查运行版本、数据库健康和下载文件完整性；没有对真实用户历史和模型执行批量分析，不将本地结果视为生产吞吐保证。
